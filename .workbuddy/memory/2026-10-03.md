## 四季之树小程序 Demo（Canvas 2D 实时渲染）

从零搭建了微信小程序工程 `season-tree`（TypeScript + Canvas 2D，不依赖 WebGL/Three.js）。

### 工程约定（后续迭代请沿用）
- 源码根目录 `miniprogram/`，`project.config.json` 通过 `useCompilerPlugins: ["typescript"]` 编译 TS。
- 类型检查：`npm run type-check`（需先 `npm install`，依赖 `miniprogram-api-typings` + `typescript`）。
- 场景坐标约定：原点在树干根部，y 向上，**1.0 = 树的总高度**；换算到画布靠 `Viewport`（原点原点 `originX/originY` + `scale`）。
- 分层：`utils/`（纯函数，零分配）→ `render/`（各子系统）→ `pages/`（只做 UI 与 setData）。
  - `TreeTrunk` = 骨架模型 + 摆动模拟（M），`BranchSystem` = 枝条渲染（V），刻意做成 M/V 分离。
  - `TreeScene` 是唯一装配点，兼 `update/render` 主循环与粒子发射调度。

### 关键设计决策（改动前请先读）
- 所有季节参数用**等距关键帧曲线**（`sampleKeyframes` / `sampleColorStops`）描述，关键帧数取 5/9/13/17，
  使 0/0.25/0.5/0.75/1.0 落在关键帧上；**每条曲线首尾值必须相等**，否则一年循环处会跳变。
- 叶片初始化一次生成固定 `Leaf[]`；每帧用 `leafAmount` 与每片叶子的静态 `threshold` 比较决定可见度，
  因此拖动时间轴时叶片位置稳定、数量连续变化。
- 颜色分桶（7 桶）合批绘制：树冠叶片、落叶粒子、地面积叶都复用同一套色板，
  极端情况下每帧 fill 也只在 23 次左右（叶子 378 片）。
- 粒子池固定 260 个对象，死亡时与末尾交换 + count--，永不扩容；
  **雪花下落速度会决定粒子池稳态水位**（速率 × 落地耗时），调参时要一起看。

### 实测数据（离线脚本验证，已删除脚本）
- 枝条 94 根 / 叶片 378 片 / 花朵 50 朵。
- 树高占画布 68.7%，在 320x568 ~ 768x1024 全部机型一致（需求 65%~75%）。
- 单帧 fill 4~23、stroke ≤2；ellipse 与降级路径结果一致，无 NaN。

### 踩过的坑
- 树冠宽高比若超过约 0.55，手机屏（接近 1:2）会先触发"按宽度适配"，树高掉到 50% 以下。
  最终把 `MAX_LEAN` 收到 0.8、`spread` 收到 0.42/0.35，才把占比拉到 68.7%。
- `ctx.ellipse` 未必所有基础库都有 → `utils/canvas.ts` 里做了能力探测 + 变换矩阵降级。
- 用 ellipse 批量成路径前必须先 `moveTo` 到椭圆起点，否则各叶片之间会被连成一张网。

### 修复：上传报 "pages/season-tree/index.js"（更关键，涉及工程约定）
- 现象：`upload failed: "pages/season-tree/index.js"`——只有路径没有原因，实为**编译产物缺失**。

  1. `tsconfig.json` 里是 `noEmit: true`，`miniprogram/` 下**只有 .ts，没有任何 .js**；发布/上传通道要的是编译后的 JS 产物。

     而发布通道打包时会按 .gitignore 过滤文件 —— 即使生成了 .js 也会被剔除。
- 修复：
  - `.gitignore` **移除** `miniprogram/**/*.js` 与 `*.js.map` 两行（并加注释说明原因，勿再改回）。只保留 `node_modules/`、`package-lock.json`、`*.log`、`.DS_Store`、`.verify/`。
  - `package.json` 新增 `"build": "tsc --noEmit false"`：就地生成 .js 到源码目录（14 个文件，`app.js` + 页面 + render/* + utils/*），与 .ts 并存。
- 校验方式：遍历 `miniprogram/**/*.js` 提取所有 `require(...)`，解析相对路径并确认目标存在 —— 38 条全部可解析；`index.js` 含 `Page({`。

### 改动
- **新增 `miniprogram/utils/weather.ts`**（+ 编译产物 weather.js）：

  - `resolveIntensity` 用**对数曲线**（`log10(mm/0.1+1)/2`）折算强度——降水量长尾分布，

## 实施优化项 3、4：颜色通道降频 + 全局兜底（19:35）

### 3. 颜色通道降频（MeshBatch）
- `MeshBatch` 的 `this.colors` 是**跨帧持久的 Float32Array**，正好可当「上次真正上传过」的基准。
  在 `write()` 里与新值比对（阈值 `COLOR_EPSILON = 1/510`，即半个 8 位色阶），
  超过才写数组并置 `colorDirty`；`commit()` 只在脏或**首次**时上传 color
  （首次必须传：GPU buffer 初始内容未定义，哪怕写入值恰好是 0）。
- **关键取舍：不能用严格相等**。季节色是连续插值，自动播放时每帧位移约 0.09/255，
  严格相等永远命中不了、通道照旧每帧重传。取半阶阈值后播放期间颜色基本稳定。
- `attributes` 数组移除 colorAttribute（几何通道留在里面），uv 仍按原逻辑 mixed 时动态。
- 缩量/清空不需要重传 color：只有 drawRange 变，缓冲区内容仍有效——已写进测试。
- **实测收益（node scripts/benchmark-render.cjs，同机器对比）**：
  樱花春 2709.6→1862.1 KiB/帧(-31%)、樱花夏 1441→1008(-30%)、红枫 2150→1481(-31%)、
  柿子秋 1640→1140(-30%)、紫薇 4530→3091(-32%)、樱花冬 204→183(-10%)。
  CPU 代价 +0.1ms/帧（0.715→0.77）。**约 1/3 的上传量换 0.1ms，非常值。**
- 紫薇仍是最重场景（3091 KiB/帧 ≈ 185MB/s @60fps），**要再降只能少画叶子**（对应待办 1/2）。

### 4. app.ts 全局兜底
- 新增 `utils/app-events.ts`：内存告警的事件总线，**不依赖 wx**（App 与 Page 都要访问，
  页面无法 import app 实例；放模块里避免循环引用，且可被 Node 测试直接 require）。
  API：`broadcastMemoryWarning(level)` / `onMemoryWarning(fn) → off()` / `highestMemoryWarningLevel()`。
- `app.ts` 从 `App({})` 扩为：`onError`、`onUnhandledRejection`（把 reason 压成一行）、
  `onLaunch` 里注册 `wx.onMemoryWarning`（**不是 App 钩子，只能用 wx.on* 注册**，需基础库 2.0.2+）、
  `onThemeChange` 仅记录不跟随（配色是设计的一部分）。
- 页面 `watchMemoryWarning()`：收到告警 → `scene.stop()` 让出显存；`onUnload` 退订防泄漏。
  **不销毁场景**（重建 WebGL 上下文比停循环贵得多）。
- `onShow` 清 `memoryPressure` 并恢复 start()——告警是瞬时信号，不能让用户盯黑屏。

### 踩坑（重要，值得记住）
- **实现缺陷被新测试抓出来**：最初 `handleMemoryWarning` 里直接 `if (scene) scene.stop()`，
  但告警可能**早于场景就绪**到达（onLoad 早于 onReady），此时 scene 为 null，事件被静默丢弃，
